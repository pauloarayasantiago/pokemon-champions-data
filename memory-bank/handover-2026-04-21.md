## Known harness bug (flag before Stage 3 reindex)

[scripts/eval-retrieval.ts:90](../scripts/eval-retrieval.ts#L90) — `matchesIdPrefix` converts dashes in `id_prefix` slug to spaces before comparing against CSV `name`/`pokemon` fields. This breaks matching for hyphenated canonical names:

- `Rotom-Wash`, `Rotom-Heat`, `Rotom-Frost` (and all Rotom forms)
- `Landorus-Therian` (adversarial case; Pokemon is banned, so the forbidden-ID check is what matters, and that works because `forbidden_ids` goes through a separate match path)
- `Tauros-Paldea-Aqua`, `Typhlosion-Hisui`, any Hisui/Paldea/Galar/Alola form

**Affected cases in current golden set:** `usage-rotom-wash`, `matchup-charizard-vs-rotom-wash`, `adv-landorus-ev` (3 of 100).

**Impact on baselines:** Both Jina-OFF and Jina-ON runs use the same buggy matcher, so **per-intent deltas and Δ tables remain valid**. Absolute numbers are slightly biased downward for the 3 affected cases. Fix before capturing the post-Stage-3 reference baseline so Stage 3's absolute numbers are clean.

**Fix** (~5 lines in [scripts/eval-retrieval.ts](../scripts/eval-retrieval.ts)):

```ts
// In matchesIdPrefix, for pokemon/move/item/usage/updated-attack cases:
case "pokemon":
  return result.source === "pokemon_champions.csv" &&
    (name === slugSpaced || name === slug);
// Same pattern for move, item, usage, updated-attack
```

The `mega:` case already handles this correctly via `replace(/\s+/g, "-").startsWith(slug)`.
